# 行程规划 Agent

单城市、多轮对话的景点行程规划：只推荐景点，不推荐住宿和餐饮。用户通过对话给出城市、日期、天数和偏好，Agent 生成草稿并支持局部修改；用户点击“确认行程”后草稿成为正式版本，之后只读。

## 接口

所有接口需要登录（`Authorization: Bearer <token>`），前缀 `/api/trips`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/` | 创建行程会话，初始状态 `collecting` |
| GET | `/` | 当前用户的行程列表 |
| GET | `/{trip_id}` | 行程详情：需求、当前草稿或已确认行程、待回答问题 |
| GET | `/{trip_id}/turns` | 对话记录 |
| POST | `/{trip_id}/messages` | 发送一条消息，请求体 `{"turn_id", "content"}`；同一 `turn_id` 重试返回首次结果 |
| POST | `/{trip_id}/confirm` | 确认草稿，请求体 `{"draft_version"}`；版本不是当前草稿时返回 409 `DRAFT_VERSION_CONFLICT` |

同一行程同时只处理一轮对话，冲突时返回 409 `TRIP_BUSY`。未配置 DeepSeek 或高德密钥时应用仍可启动，发送消息返回服务不可用。

## 生命周期与存储

`collecting`（收集需求，可换城市）→ `drafting`（第一版草稿生成后城市锁定，天数、日期、偏好、节奏等仍可修改）→ `confirmed`（只读）。

| 表 | 说明 |
| --- | --- |
| `trips` | 会话：状态、城市、当前需求、待回答问题、当前草稿版本、确认版本、单轮租约锁 |
| `trip_plan_versions` | 草稿版本，只追加不更新；撤销也会生成新版本 |
| `trip_turns` | 每轮的 user/assistant 两条消息，唯一键保证重试幂等 |
| `poi_profiles` | 景点属性（细分体验、室内外、建议游玩分钟数）的全局缓存，与会话无关 |

建表语句见 `scripts/trip_agents.sql`，应用启动不会自动建表。旧版本留下的 `attractions`、`planning_tasks`、`trip_confirmations`、`trip_drafts`、`trip_messages`、`trip_sessions`、`trip_versions` 表不再使用，也不会被修改。

### 为什么不用 checkpointer 和 interrupt

每条用户消息是一次完整的图执行。需求、草稿版本、待回答问题都保存在 MySQL 中，由 Service 读取快照传入图、按结果条件写回（保存与确认都带乐观锁）。待回答问题作为数据保存，用户下一条消息按普通输入处理，因此不需要 interrupt/resume，也避免了检查点与业务表两份状态不一致。

## 图结构

根图 `app/agent/trip/trip_graph.py`：

```text
understand → resolve ─┬─ plan → render
                      ├─ qa
                      └─ render
```

- `understand`：规则快速路径（选项序号、撤销、确认等）优先，其余调用 DeepSeek 结构化输出得到意图。有待回答问题时“确认”类回复不走快速路径，交给模型判断是否在回答问题。
- `resolve`：`IntentResolver` 把意图落到需求和修改操作上，用高德核实景点名称；名称有歧义时给出选项。用户放弃本次修改（`cancel`）时保持原样并清除待回答问题；范围外请求或闲聊里夹带了需求变化时（非已确认状态），需求照常生效，范围外部分作为说明回复。
- `plan`：调用规划子图。
- `qa`：问答 Agent（`create_agent`），工具为高德地点查询、当前草稿，配置博查密钥时再加网页搜索；工具调用和模型调用次数都有上限。
- `render`：生成回复文字，包括变化摘要和补位说明。

规划子图 `app/agent/trip/planning/planning_graph.py`：

```text
scope → gather → enrich → solve ─┬─ expand → gather
                                 ├─ widen  → enrich
                                 ├─ validate
                                 └─ diagnose
```

- `scope`：首次规划或全局变化时全量规划；删除、替换、新增、移动、交换、调整时长、调整某天松紧都是局部修改，只求解受影响的天。
- `gather`：用固定模板（`城市+热门景点`、`城市+必去景点`、`城市+旅游景点`，以及偏好或替换目标对应的关键词）搜索高德，同时获取天气预报。
- `enrich`：确定候选集，补全景点属性（先查缓存，缺失的批量调用模型，失败按规则推断）。
- `solve`：OR-Tools CP-SAT 求解选点、分天、排序和时间。
- `expand`：候选不足时多搜一轮；`widen`：局部求解无解时放宽范围；`validate`：独立验算草稿；`diagnose`：给出失败原因和可选操作。

## 候选集规则

1. 只搜索风景名胜、博物馆、展览馆、美术馆分类，排除跨城市结果、景区附属设施（停车场、售票处、索道等）和暂停开放的地点；同名地点只保留一个。
2. 景区与其内部景点同时出现时：父景区有 3 个及以上子景点则保留子景点（如西湖风景名胜区下的曲院风荷、花港观鱼），否则保留父景区。名称中的“某某风景名胜区-”“某某风景名胜区”前缀会被去掉（如“杭州西湖风景名胜区宝石山”显示为“宝石山”）。
3. 用户必去、新增的景点，以及局部修改中受影响天的原景点无条件保留，没有评分也保留。
4. 其余地点必须有可解析的高德评分：默认只取评分 ≥ 4.5 的地点（按命中模板数、评分降序）；不足时从剩余有评分的地点中按评分降序补入。
5. 有替换约束（如“换成一个博物馆”）时，每个约束先预留至多 5 个满足条件的有评分地点，避免同类地点因热度不足被上限挤掉。
6. 候选集总数不超过 35 个（7 天 × 每天最多 5 个）。

## 规划规则

- 只支持 1～7 天；每天游玩时间窗 9:00–19:00，午餐 1 小时由求解器安排；不考虑开放时间。
- 每天景点数上限：休闲 3 个、适中 4 个、紧凑 5 个；休闲节奏 17:30 前结束。“某天轻松一点”减 1 个并提前 90 分钟结束，“某天充实一点”加 1 个（不超过 5 个）并可排到 19:00。
- 游玩时长由模型建议，用户可以单独调整。
- 交通按直线距离估算：步行分钟 ⌈d×1.3÷4.5×60⌉+5，打车分钟 ⌈d×1.4÷25×60⌉+15；直线 ≤ 1.5 km 且步行不超过用户上限时步行，否则打车；用户要求只步行时不受 1.5 km 限制。单段超过 120 分钟视为不可达。步行费用为 0，打车费用只有配置了可信城市费率才估算。不含往返住宿。
- 目标：最大化 Σ兴趣分 + Σ评分质量分 + 6×景点数 − 每日同主体验类集中惩罚 − 3×Σmax(同细分体验次数−2, 0) − 交通总分钟÷15 − 3×Σ雨天惩罚单位；局部修改时保留原景点有额外奖励。雨天惩罚单位按访问计：室内为 0，户外为降雨等级（0～3）× 时长档，半室内为降雨等级 × max(1, 时长档 // 2)；时长档 ≤ 90 分钟为 1、≤ 180 分钟为 2、更长为 3。兴趣分为景点标签 × 用户偏好权重：权重 1/2 表示喜欢/非常喜欢，-1 表示不喜欢、少安排（命中喜欢的标签时以喜欢为准；只设置了不喜欢时，其他景点按中性分）。
- 替换目标、选择器的标签：同一维度内任一满足、不同维度同时满足，例如“博物馆或美术馆”“户外的寺庙”。
- 删除或移出后当天空出 ≥ 60 分钟才补入新景点，并在回复里说明。
- 局部求解无解时依次放宽：固定原景点 → 原景点软保留 → 纳入相邻天；仍无解时询问用户是否允许调整其他天。

## 返回给前端的景点字段

草稿 `plan.days[].items[]` 中每个景点包含 `poi_id`、`name`、`lng`、`lat`、`address`、`rating`（可空）、`photos`、开始/结束分钟、游玩时长、与上一个景点之间的交通段等。`photos` 来自高德 `extensions=all` 返回，最多 5 张，形如：

```json
[{"url": "https://store.is.autonavi.com/showpic/...", "title": "夏季"}]
```

图片地址统一为 https；高德标题为空时 `title` 为空串。
